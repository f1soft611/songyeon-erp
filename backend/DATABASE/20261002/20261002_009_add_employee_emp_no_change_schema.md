# 20261002_009 직원번호(emp_no) 칸 추가 변경 이력

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-02 |
| 대상 DB | songyeon (PostgreSQL) |
| 유형 | 칸 추가 + 유일 색인 + 데이터 1건 |
| 대상 표 | employees (`emp_no VARCHAR(20)`, `idx_employees_emp_no` 부분 유일 색인, id 1 → `'0000'`) |
| 적용 | 2026-10-02 적용 → 롤백(사용자가 칸 없이 하자고 함) → 다시 적용(칸 없이는 송연 원본을 지킬 방법이 없어 사용자 확인). 지금 emp_no 있음, 관리자 = '0000' |
| 롤백 | `20261002_009_rollback.sql` (색인·칸 삭제) |

## 이유

- 사용자 요청: 이 프로젝트에서는 '0000' 으로 로그인하고, 송연 원본은 지금처럼 '관리자' 로 로그인한다.
- 칸 없이 `id` 를 바꾸는 방법은 원본을 깨뜨린다: `id` 를 0 으로 하면 원본이 `if not session.get("employee_id")` 로 로그인 여부를 보아 0 을 '로그인 안 됨' 으로 봐 관리자가 원본에서 튕기고, 글자 칸으로 바꾸면 원본의 숫자 비교(대시보드 메모·직원 관리)가 오류.
- 처음에는 `employees.id`(숫자)를 '0000'(글자)으로 바꾸는 안이었으나, 송연 원본이 `id` 를 숫자로 다른 표(대시보드 메모 등)와 잇고 `WHERE id = ?` 로 찾아 칸 종류를 바꾸면 원본이 깨진다. 그래서 `id`·`username` 은 그대로 두고 글자 칸 `emp_no` 를 더했다(사용자 확인).
- 참고: 20261002_008(username 을 '0000' 으로)은 잘못 이해한 변경이라 같은 날 롤백 스크립트로 되돌렸다(username = '관리자').

## 영향 범위

- 이 프로젝트 로그인(`actionLoginEmployee`)은 직원번호(`emp_no`)로 찾는다. 직원번호가 아직 없는 직원은 기존처럼 `username` 으로 로그인(막히지 않게). 내 정보 관리의 '아이디' 는 직원번호(없으면 username).
- 송연 원본은 `emp_no` 를 모르므로 지금처럼 `username` 으로만 로그인 — 영향 없음.
